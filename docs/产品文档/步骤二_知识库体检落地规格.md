# 步骤二 · 知识库体检层落地规格

> 版本 v0.3 · 2026-08-28
> 定位：**Agent 自主决策规格**。不是产品经理写死指标，而是 Agent 读库后**自动分析库的关系逻辑 → 自创指标体系 → 定义指标含义 → 输出评估 → 让用户看见**。
> 依赖：步骤一已完成，博主画像 + 三库资产已落库。

---

## 0. 本步骤的目标（可验收）

给定一个博主的资产库（三库已建），Agent 能自动：

1. **读取分析**三库的关系逻辑与重点（库之间怎么关联、哪些是核心资产）
2. **自创指标体系**：根据库的实际内容，自动生成评价指标（不是预设的）
3. **定义指标含义**：告诉用户每个指标反映什么业务含义
4. **输出评估结果**：按自创的指标评估当前库
5. **输出功能建议**：基于评估结果，告知当前数据能支持哪些功能
6. **全部可追溯**：决策落 decision_log，展示给用户看

**验收线**：Agent 读库 → 输出"我定义了 3 个指标：知识完备度（反映类别覆盖）、素材丰富度（反映创作能力）、算法匹配度（反映推流潜力）→ 评估结果：美食类 85 分，非遗类 40 分 → 当前可支持脚本撰写，AIGC 需补素材"。

---

## 1. 体检的输入

| 输入 | 来源 | 用途 |
|---|---|---|
| 博主画像 | blogger 表 | 了解博主的定位/风格/变现目标 |
| 当前资产库 | asset 表（三库全部条目） | Agent 分析库关系与逻辑 |
| 产出引用记录 | output 表（引用关系） | 了解哪些资产被用过、产出与库的关联 |
| 历史决策记录 | decision_log | 可参考历史判断，但本轮体检独立决策 |
| **资产有效性** | asset 表(effect) | 反馈环节标记的「有效/待审视」资产，列入薄弱环节分析 |

**Agent 读库时自动分析什么**：
- 三库各自的结构：分类分布、条目密度、可信度分布
- 库间关系：知识库条目被素材库引用？素材库与算法库是否有重叠？
- 重点资产：哪些条目/分类被产出多次引用（核心资产）
- 薄弱环节：哪些分类条目少、可信度低、未被引用

  │

```

## 3. Agent 自创指标体系的规则框架

> 产品经理不给死指标，但给 Agent **生成指标的规则框架**。Agent 在这个框架内自由发挥。

### 3.1 指标生成规则（Agent 必须遵守）

| 规则 | 内容 |
|---|---|
| 规则1 | **至少 3 个指标**，不设上限。 |
| 规则2 | 每个指标必须包含：**名称 + 含义 + 评分逻辑(0-100) + 业务含义**（这个指标反映什么）。 |
| 规则3 | 指标必须基于**库的实际内容**生成，不能凭空造。 |
| 规则4 | 指标必须覆盖**三库关系**（不能只看单库，要反映库间关联）。 |
| 规则5 | 必须给出各指标的**权重**，说明为什么这样分配。 |
| 规则6 | 输出必须包含**业务解释**：这些指标合起来告诉用户什么。 |

### 3.2 Agent 生成指标时必须回答的问题（引导 Agent 思考）

```
【关于库关系】
- 三库之间是怎么关联的？知识库支撑素材库？算法库指引知识库？
- 哪些条目/分类是核心节点（被多次引用）？
- 哪些条目/分类是孤岛（无引用、无关联）？

【关于指标】
- 基于以上分析，我应该定义什么指标来评价这个库？
- 每个指标的业务含义是什么？（用户看到这个指标能理解什么？）
- 这些指标合起来，能反映库的什么整体状态？
```

### 3.3 指标示例（Agent 生成的，不是预设）

> 以下仅为示例，实际指标由 Agent 根据库内容自行生成，可能完全不同。

| 指标名称 | 含义 | 评分逻辑 | 反映什么业务 |
|---|---|---|---|
| 知识完备度 | 知识库覆盖博主应有的内容范畴的程度 | 0-100，按应有分类 vs 实际计算 | 博主"有东西可讲"的程度 |
| 素材丰富度 | 素材库为创作提供的模板/工具充分程度 | 0-100，按主风格模板数量+多样性 | 博主"拍得出来"的能力 |
| 算法匹配度 | 算法库与博主平台/变现的匹配程度 | 0-100，按平台机制+标签+变现逻辑覆盖 | 博主"能被推流"的潜力 |
| 库间关联度 | 三库之间互相引用的紧密程度 | 0-100，按引用关系密度 | 库是否"活"的（不是各存各的） |

> **关键**：Agent 可能定义 3 个、5 个、甚至 7 个指标。可能叫法完全不同。只要在规则框架内，Agent 说了算。

## 4. Agent 体检提示词（可直接使用）

```
你是贵州文旅知识库体检 Agent。你的核心职责是：**自创指标体系，评估库的有效性，并告诉用户这些指标反映了什么**。

【博主画像】
{结构化画像}

【当前资产库（完整）】
{asset 表全部条目：所属库/分类/标题/内容/标签/来源/可信度}
{output 表：产出引用关系}
{decision_log：历史决策记录}

【你的工作流】

第一步：读库分析
分析三库的结构、关系逻辑与重点：
- 三库各自的结构：分类分布、条目密度、可信度分布
- 库间关系：知识库条目被素材库引用？哪些条目是核心节点？
- 重点资产：哪些条目/分类被产出多次引用？
- 薄弱环节：哪些分类条目少、可信度低、未被引用？
- 资产有效性：反馈环节标记的「待审视」资产 → 列入薄弱环节

第二步：自创指标体系
基于以上分析，定义评价指标（至少 3 个，不设上限）：
每个指标必须包含：
- 名称：简短
- 含义：一句话说明
- 评分逻辑：0-100 怎么算
- 业务含义：这个指标反映什么（用户看到这个应该理解什么）
- 权重：各指标权重 + 为什么这样分配

第三步：按自创指标评估当前库
逐项打分，给出理由。

第四步：输出功能建议
基于评估结果，判断当前数据能支持哪些功能（如脚本撰写、AIGC 生成等），
未就绪的告知还差什么。

【硬约束】
- 指标必须基于库的实际内容生成，不能凭空造
- 指标必须覆盖三库关系
- 每个判断必须给出 reason
- 不编造：不臆测不存在的条目
- 输出结构化 JSON

【输出格式】
{

  "library_analysis": {
    "structure": { "knowledge": {...}, "material": {...}, "algorithm": {...} },
    "relations": "库间关系分析...",

    "weak_spots": ["薄弱环节1"]

      "business_meaning": "反映博主"有东西可讲"的程度",
      "score": 75,
      "weight": "30%",

      "reason": "美食类完备，非遗类缺 3 项"
    }

  "overall_score": 72,
  "feature_readiness": [
    {
      "feature": "脚本撰写",

## 5. 表结构（体检结果的落点）

### 5.1 assessment 体检记录表

```sql
CREATE TABLE assessment (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id      INTEGER NOT NULL REFERENCES blogger(id),
  library_analysis TEXT,             -- 库关系分析 JSON
  indicators      TEXT,              -- Agent 自创指标体系 JSON（含含义/权重/评分逻辑/业务含义）
  overall_score   INTEGER,           -- 综合分 0-100
  feature_readiness TEXT,            -- 功能就绪度 JSON
  suggestions     TEXT,              -- 改进建议 JSON
  decision_id     INTEGER,           -- 关联决策记录
  created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 5.2 关系补充

```
blogger 1—n assessment   （一个博主多次体检）
assessment n—1 decision_log （每次体检关联一个决策记录）
```

## 6. 展示给用户（前端）

### 6.1 展示区块

| 区块 | 内容 | 目的 |
|---|---|---|
| **库关系图** | 三库结构 + 核心节点 + 薄弱环节（Agent 分析） | 让用户看到"我的库长什么样" |
| **指标体系卡** | 每个指标一行：名称 / 含义 / 业务含义 / 权重 / 评分 / 理由 | 让用户看到"Agent 用什么标准评价" |
| **综合分** | 加权总分 | 快速感知 |
| **功能就绪卡** | 每个功能一张卡：就绪/未就绪 + 还差什么 | 让用户知道"我现在能做什么" |
| **改进建议** | 按优先级排序 | 让用户知道"下一步补什么" |

### 6.2 展示要点

- **用户能看到"Agent 为什么定义这些指标"**：指标卡的"业务含义"字段解释给用户听
- **用户能看到"Agent 的评分依据"**：每条评分附 reason
- **用户能看到"功能就绪的因果关系"**：未就绪 → 明确告知差哪库、差多少
- **用户可对比历史体检**：之前体检的指标体系和现在可能不同（Agent 每次可能定义不同指标）

## 7. 落地执行步骤

```
Step 0 输入：从 blogger + asset + output + decision_log 取当前博主数据
Step 1 Agent 读库分析：分析三库结构、关系逻辑与重点
Step 2 Agent 自创指标体系：定义 N 个指标（名称/含义/评分逻辑/业务含义/权重）
Step 3 Agent 评估：按自创指标逐项打分 + 功能就绪度判断
Step 4 落库：写 assessment 表 + decision_log（decision_type=assess）
Step 5 展示：前端渲染体检报告（§6.1 区块），就绪功能变可点按钮
Step 6 联动：就绪功能 → 跳转步骤三（产出层）
Step 7 验收：§8 验收标准逐条过
```

## 8. 验收标准（Agent 自测）

| # | 验收项 | 通过标准 |
|---|---|---|
| B1 | 读库分析 | 输出三库结构+关系分析+核心资产+薄弱环节 |
| B2 | 自创指标 | 至少 3 个指标，每个有名称/含义/评分逻辑/业务含义/权重 |
| B3 | 业务含义清晰 | 每个指标的 business_meaning 能让用户理解"这个指标反映什么" |
| B4 | 覆盖三库关系 | 指标不是单库评估，反映库间关联 |
| B5 | 功能就绪度 | 基于评估结果判断功能是否就绪，未就绪含"还差什么" |
| B6 | 决策可追溯 | decision_log 有本次体检记录，含 decision + reason |
| B7 | 记录可查 | assessment 表有本次体检记录，历史可查 |
| B8 | 可对比 | 两次体检的指标体系可能不同（Agent 每次自创），历史记录可对比 |

## 9. 边界与约束

- **指标不预设**：产品经理不给死指标，Agent 每次可能定义不同指标。
- **必须可解释**：每个指标必须有业务含义，让用户理解"为什么评这个分"。
- **不编造**：指标必须基于库内真实内容，不能凭空创造。
- **失败降级**：Agent 无法评估时返回明确错误，不输出垃圾报告。
