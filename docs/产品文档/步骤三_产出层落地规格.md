# 步骤三 · 产出层落地规格

> 版本 v0.1 · 2026-08-28
> 定位：**Agent 自主决策规格**。产出不是模板填空，而是 Agent 综合**画像 + 知识库 + 体检结果**自主决策生成脚本/分镜/路线，全部可追溯、可落地。
> 依赖：步骤一（画像+建库）、步骤二（体检）已完成。体检输出的"就绪功能"决定本层能产出什么。

---

## 0. 本步骤的目标（可验收）

给定一个博主（画像 + 三库 + 体检结果已就绪），Agent 能自动：
1. **生成脚本**：按博主风格，基于知识库内容，产出可直接用的脚本/分镜
2. **生成路线推荐**：基于画像 + 知识库 + 商单目标，产出排序后的探店打卡路线
3. 每次产出**关联画像**（产出人/风格）、**关联知识库引用**（用的哪些资产）
4. 产出**落 output 表**，**可追溯**（decision_log）
5. 产出**可被反馈环节引用**（为步骤四反馈做铺垫）

**验收线**：非遗美食博主 → 产出"以酸汤鱼为切入点的非遗探店脚本"+ "凯里酸汤鱼→西江苗寨"路线推荐 → 落 output 表 → 关联画像与知识库引用 → 可录入反馈。

---

## 1. 产出层的输入

| 输入 | 来源 | 用途 |
|---|---|---|
| 博主画像 | blogger 表 | 风格/平台/内容类型/变现/常跑路线 |
| 三库资产 | asset 表 | 知识库（内容事实）、素材库（风格模板）、算法库（平台机制） |
| **店铺库** | place 表 | **收益属性（成本/收益/喜爱度/适合KOC与拍摄）→ 路线收益最大化依据** |
| 体检结果 | assessment 表 | 就绪功能/缺口，决定能产出什么 |
| 用户指令 | 用户输入 | 用户可指定主题/方向，也可让 Agent 自由发挥 |

**关键**：产出不是凭空创作，是**基于库的"有依据创作"**——引用真实知识、套用博主风格、遵循平台机制。

---

## 2. 产出类型

| 类型 | 产出内容 | 依据 |
|---|---|---|
| **脚本 script** | 可直接拍摄的口播/vlog脚本（含开头/正文/结尾/节奏） | 画像风格 + 知识库内容 + 算法库平台机制 |
| **分镜 storyboard** | 脚本的画面拆解（镜头/画面/台词/时长） | 素材库模板 + 脚本内容 |
| **路线推荐 route_rec** | 拍摄/KOC 路线（地点/顺序/成本/收益/净收益/契合理由，按收益最大化排序） | 画像 + 店铺库收益属性 + 知识库 + route 表 |
| **内容规划 schedule_plan** | 未来 N 天的发布排期（哪天发什么/哪个平台/类型） | 画像更新频率 + 已有产出 |
| **发布 publish** | 一键发布到各平台（MVP=模拟发布，标记已发布） | 排期内容 |
| **自动回收 auto_collect** | 定时从平台回收数据落 metric 表 | 已发布内容 + 平台数据 |

> MVP 产出脚本 + 分镜 + 路线。AIGC 视频为后续版本（步骤二体检可判定"AIGC 就绪"后接入）。

## 3. Agent 产出决策（Agent 自主）

### 3.1 脚本生成

**Agent 做什么**：
1. **读画像**：风格（口播/vlog/剧情）、平台（时长/节奏）、内容类型（主题方向）
2. **读知识库**：找该主题的**可信条目**（来源实锤/官方），作为内容依据
3. **读素材库**：套用该风格的**开头模板/钩子/转场/BGM建议**
4. **读算法库**：遵循平台机制（开头 3 秒钩子、时长、标签、发布时间建议）
5. **自主决策**：主题（用户指定或 Agent 选）、结构（开头-正文-结尾）、节奏、标签

**脚本结构（Agent 可自定义，参考如下）**：
```
【标题】
【风格标签】口播/时长 60s
【开头 0-5s】钩子："你绝对没吃过的酸汤鱼，就藏在凯里巷子里"
【正文 5-50s】知识点+探店过程（引用知识库可信条目）
【结尾 50-60s】钩子+引导："关注我，下期带你去西江"
【标签】#贵州美食 #非遗 #凯里
【分镜】见分镜生成
```

### 3.2 分镜生成

**Agent 做什么**：把脚本拆成分镜（每个镜头：画面/台词/时长/BGM/转场），套用素材库模板。

```
【分镜表】
镜头1 0-5s  | 画面：巷子口全景+酸汤鱼特写 | 台词：钩子 | BGM：快节奏 | 转场：切
镜头2 5-25s | 画面：制作过程/老板手部特写 | 台词：知识讲解 | BGM：渐入 | 转场：叠化
镜头3 25-45s| 画面：博主试吃/表情 | 台词：体验感 | BGM：高潮 | 转场：切
镜头4 45-60s| 画面：回眸/招牌特写 | 台词：引导关注 | BGM：渐弱 | 转场：淡出
```

### 3.3 路线推荐（收益最大化）

> **核心**：路线推荐不是为了"拍一条内容"，而是**帮博主排拍摄/KOC 路线，最大化收益**。依据是店铺库（place 表）的**收益属性**：预估收益、成本、博主喜爱度、是否适合 KOC/拍摄。

**Agent 做什么**：
1. **读画像**：变现方式（商单/探店/带货）、内容类型、常跑路线、粉丝量级
2. **读店铺库 place 表**：每家店的 收益属性（est_cost / est_benefit / like_level / fits_koc / fits_shoot）
3. **读知识库**：店铺的文化/招牌（作为内容依据）
4. **组合与排序**：
   - 选出适合拍摄/KOC 的店（fits_shoot=1 或 fits_koc=1）
   - 综合 `est_benefit - est_cost`（净收益）+ `like_level`（博主喜欢）+ 画像契合度，做**收益最大化排序**
   - 相邻店可串成一条路线（地理相近/同类别）
5. **自主决策**：输出排序后的路线，每条标注 成本/收益/净收益/契合理由

**路线推荐输出**：
```
【推荐路线】（按净收益排序）
1. 凯里酸汤鱼店→西江苗寨长桌宴（净收益 +700）
   途经：凯里巷子/西江苗寨/长桌宴
   成本：800 | 收益预估：1500 | 博主喜爱度 5/5
   推荐理由：博主喜欢的店(fits_koc=1)+高收益，非遗美食高度契合
2. 雷山银球茶体验→丹寨蜡染工坊（净收益 +500）
   ...
```

### 3.4 内容规划（排期 + 执行 + 提醒）

> **核心新增**：产出不只是脚本，还要有**排期规划**——哪天发什么，让博主好执行、到时间会提醒。规划输出 → 排期 schedule 表。

**Agent 做什么**：
1. **读画像**：更新频率（日更/周更/不定期）、平台、内容类型
2. **读产出**：当前已生成的脚本/路线（output 表），作为排期素材
3. **自主决策**：
   - 规划未来 N 天的发布计划（哪天发什么、发哪个平台、什么类型）
   - 排期密度 = 匹配博主更新频率（日更就每天排，周更就每周排）
   - 排期内容 = 从已有产出中选择，或 Agent 补充生成
4. **输出排期表**：日期/内容/平台/类型/状态

**排期表输出**：
```
【内容排期规划】
周一 9/1  | 抖音 | 酸汤鱼探店脚本 | 待发布
周二 9/2  | 小红书 | 苗绣图文 | 待发布
周三 9/3  | 抖音 | 西江苗寨路线 | 待发布
周四 9/4  | B站 | 酸汤鱼制作vlog | 待生成
```

**提醒机制**：
- 排期表的 `status` 字段：`待发布` → `已发布` → `已回收数据`
- 系统定时检查：**到发布日当天 → 提醒博主"今天该发这个了"**（前端通知/弹窗/列表高亮）
- 博主发布后 → 手动标记"已发布" → 触发**定时自动回收**（见 §3.6）

### 3.5 一键发布

> **目的**：排定内容后，从系统一键发布到各平台。MVP 做**模拟发布**（关键是真跑演示闭环），发布后标记已发布并触发定时回收。

**Agent 做什么**：
1. 博主选择某条排期内容 → 点【发布】
2. 系统读该内容的平台/内容/格式
3. 执行发布动作（MVP 阶段=标记已发布+记录发布时间，后续可接真实 API）
4. 发布后 → 排期 status 更新为"已发布" → 触发定时回收

**发布记录输出**：
```json
{
  "publish_time": "2026-09-01 10:00",
  "platform": "抖音",
  "content_id": output_id,
  "status": "已发布"
}
```

### 3.6 定时自动回收反馈

> **目的**：内容发布后，系统**定时自动从各平台收集数据**（播放/点赞/评论/收藏），落 metric 表，无需博主手动录入。这是"让步骤四的报告生成有数据"的关键。

**Agent 做什么**：
1. 定时检查：排期表中 status=已发布 且 未回收/距上次回收>N 小时
2. 对每条已发布内容，从各平台取数（MVP 阶段=模拟取数，演示定时自动回收的逻辑）
3. 落 metric 表：output_id / views / likes / comments / collects / recorded_at
4. 更新时间：排期 status 更新为"已回收数据"
5. 触发步骤四：反馈闭环 + 报告生成

**自动回收提示**：
```
【系统自动回收】
酸汤鱼探店 → 抖音
播放：12000 | 点赞：850 | 评论：230 | 收藏：410
已录入 metric 表，将触发反馈分析与报告更新。
```

**定时规则**（Agent 可配置，但建议 MVP 就做"手动触发自动回收"演示）：
| 场景 | 回收时机 |
|---|---|
| 发布后立即 | 发布后 1 小时首轮回收 |
| 常规回收 | 每天定时回收一次 |
| 手动触发 | 用户可随时点"回收数据" |
| 因素 | 权重倾向 | 说明 |
|---|---|---|
| 净收益 est_benefit - est_cost | 高 | 帮博主赚钱是核心目标 |
| 博主喜爱度 like_level | 高 | 博主喜欢的店拍起来自然、真实 |
| 是否适合 KOC/拍摄 | 高 | fits_koc=1 优先（可接商单） |
| 与画像契合 | 中 | 内容方向一致（非遗博主→非遗店） |

## 5. 表结构扩展（产出的落点）

### 5.1 output 表（扩展引用关系）

```sql
CREATE TABLE output (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id   INTEGER NOT NULL REFERENCES blogger(id),
  type         TEXT NOT NULL,     -- script|storyboard|route_rec
  category     TEXT,              -- 内容/主题分类(Agent自定义，如"美食探店")，报告"内容类型分布"用它聚合
  title        TEXT NOT NULL,
  content      TEXT NOT NULL,     -- 产出正文(JSON，含结构)
  source_refs  TEXT,              -- 引用的资产 id 列表(JSON，可追溯)
  decision_id  INTEGER,           -- 关联决策记录
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 5.2 新增 output_asset 产出-资产引用表（关联产出与库）

```sql
CREATE TABLE output_asset (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  output_id   INTEGER NOT NULL REFERENCES output(id),
  asset_id    INTEGER NOT NULL REFERENCES asset(id)
);
```

> **用途**：记录"这条产出用了哪些知识库/素材/算法条目"——反馈环节据此后续判断"哪些资产有效"，并**反查脚本/分镜涉及的店铺**（asset 有 place_id 时）。

### 5.3 新增 schedule 排期表（内容规划）

```sql
CREATE TABLE schedule (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id   INTEGER NOT NULL REFERENCES blogger(id),
  plan_date    TEXT NOT NULL,     -- 计划发布日期
  platform     TEXT NOT NULL,     -- 平台
  output_id    INTEGER REFERENCES output(id),  -- 关联产出(可空:未生成时为空)
  content_type TEXT,              -- 视频|图文
  title        TEXT,
  status       TEXT DEFAULT '待发布',  -- 待发布|已发布|已回收数据
  publish_time TEXT,              -- 实际发布时间
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

> **提醒机制**：系统定时检查 schedule，到 plan_date 当天且 status=待发布 → 提醒博主"今天该发这个了"。
> **发布**：博主点发布 → status=已发布 + publish_time 记录。
> **回收**：定时/手动触发 → 从平台取数落 metric → status=已回收数据。

### 5.4 关系补充

```
blogger 1—n output
output 1—n output_asset
asset 1—n output_asset
output 1—n metric   （产出被录入反馈）
```

## 6. 检索与展示

### 6.1 产出记录
```sql
SELECT * FROM output WHERE blogger_id=? ORDER BY created_at DESC
SELECT * FROM output_asset WHERE output_id=?  -- 看产出引用了哪些资产
SELECT * FROM schedule WHERE blogger_id=? ORDER BY plan_date  -- 看排期
SELECT * FROM schedule WHERE plan_date=date('now') AND status='待发布'  -- 今日待发布(提醒)
```

### 6.2 展示给博主（前端）
| 区块 | 内容 |
|---|---|
| 脚本卡 | 完整脚本（标题/风格/开头/正文/结尾/标签）+ 引用来源标注 |
| 分镜表 | 镜头/画面/台词/时长/BGM/转场 |
| 路线卡 | 排序后的路线 + 成本/收益/净收益/契合理由 |
| **排期表** | 未来 N 天计划：日期/内容/平台/类型/状态 + 倒计时（今天待发布高亮） |
| **发布按钮** | 每条排期内容可点【发布】，发布后状态变已发布 |
| **回收状态** | 已发布内容显示"已回收/待回收"，回收后显示数据 |
| 引用溯源 | 展开可看"这条产出用了哪些知识库条目" |

## 7. 落地执行步骤

```
Step 0 输入：从 blogger + asset + place + assessment + output 取当前博主数据 + 用户指令
Step 1 Agent 产出：按 §4 提示词生成脚本/分镜/路线/内容排期
Step 2 落库：写 output 表 + output_asset 引用 + schedule 排期 + decision_log（decision_type=generate）
Step 3 展示：前端渲染产出（§6.2 区块），路线卡含净收益/喜爱度，排期表含倒计时
Step 4 发布：博主选排期内容点【发布】→ status=已发布 + 记录时间
Step 5 提醒：系统定时检查 schedule → 到 plan_date 且待发布 → 提醒博主"今天该发这个了"
Step 6 自动回收：定时/手动触发 → 从平台取数落 metric 表 → status=已回收数据
Step 7 联动：反馈数据触发步骤四（反馈闭环 + 报告生成）
Step 8 验收：§9 验收标准逐条过
```

## 8. 验收标准（Agent 自测）

| # | 验收项 | 通过标准 |
|---|---|---|
| C1 | 脚本生成 | 生成贴合博主风格的完整脚本（标题/**分类**/开头/正文/结尾/标签） |
| C2 | 分镜生成 | 脚本拆成分镜表（镜头/画面/台词/时长/BGM/转场） |
| C3 | 路线推荐 | 输出排序后的路线，含成本/收益/净收益/契合理由 |
| C4 | **收益最大化** | 路线按收益属性排序（净收益高/喜爱度高的店排前） |
| C5 | **店铺依据** | 路线基于 place 表收益属性（est_benefit/est_cost/fits_koc/fits_shoot） |
| C6 | 基于库创作 | 脚本引用知识库可信条目（source_refs 非空），不编造事实 |
| C7 | 风格贴合 | 脚本风格与博主画像一致（不是通用模板） |
| C8 | 平台匹配 | 平台机制符合博主平台（时长/节奏/标签） |
| C9 | 引用可追溯 | output_asset 记录产出与资产引用关系 |
| C10 | 决策可追溯 | decision_log 有本次产出记录，含 decision + reason |
| C11 | **内容排期** | schedule 表生成未来 N 天排期（日期/平台/类型/状态），匹配更新频率 |
| C12 | **执行提醒** | 到 plan_date 且待发布 → 系统提醒博主"今天该发这个了" |
| C13 | **一键发布** | 点发布 → status=已发布 + 记录发布时间 |
| C14 | **定时自动回收** | 已发布内容自动回收平台数据落 metric 表，status=已回收数据 |

## 9. 边界与约束

- **不编造**：产出内容必须引用知识库可信条目，禁止编造事实。
- **风格贴合**：产出不是通用模板，必须贴合博主画像。
- **联动体检**：体检未就绪的功能，产出层不强行生成（如 AIGC 未就绪则不生成视频）。
- **排期可执行**：内容规划必须匹配博主更新频率，博主能按排期执行。
- **提醒不打扰**：提醒机制到点触发一次，不重复轰炸。
- **失败降级**：Agent 无法产出时返回明确错误。
