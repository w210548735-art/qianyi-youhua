# 步骤四 · 反馈闭环 + 报告生成落地规格

> 版本 v0.2 · 2026-08-28
> 定位：**Agent 自主决策规格**。录入真实指标（含定时自动回收）→ Agent 分析博主适合类型/踩雷点 → 写回画像 + 回写店铺收益 → **库进化：更新三库（知识/素材/算法）+ 算法打法 + 创作方向** → **读取指标表做数据分析 → 生成带图表的最终报告**（告诉博主赚钱没/亏钱没/流量怎么样）→ 下一次产出更准（**闭环合上**）。
>
> **闭环的真正含义（用户定义）**：「**反馈过来 → 更新我的这几个库（知识库/素材库/算法库）+ 几个算法（算法打法）+ 几个方向（主攻方向/适合类型）**」——不是只改一个画像字段，而是**反馈反哺整套库与方向**，下次建库/产出/推荐全部基于更新后的库运行。
> 依赖：步骤一/二/三已完成（画像/库/店铺/产出/指标体系已存在）。

---

## 0. 本步骤的目标（可验收）

给定真实数据（人工录入 + 定时自动回收），Agent 能自动：
1. **收集反馈**：人工录入 + **定时自动回收各平台数据**落 metric 表
2. **Agent 分析**：基于指标 + 内容特征 → 判断博主**适合的视频类型 / 踩雷点**
3. **写回画像**：更新 blogger.suit_type（适合的视频类型）
4. **回写店铺收益**：该产出涉及的店铺，真实收益回写 place 表 → 更新收益排序
5. **更新指标体系**：按 indicator 表的 formula 从各表取数，更新 current/trend
6. **生成最终报告**：读指标表 → 数据分析 → **带图表**（折线图/柱状图）→ 告诉博主**赚钱没/亏钱没/流量怎么样/供应商怎么样**
7. **库进化（闭环核心）**：产出反馈 → Agent **更新三库（知识/素材/算法条目）+ 算法打法 + 创作方向** → 下次建库/产出基于更新后的库更准
8. **全部可追溯**：落 decision_log

**验收线**：录入"美食探店员 1万播放 800评论，纯风景vlog 播放惨淡"→ 系统判"适合美食+探店，风景踩雷"→ 写回画像 → 相关店铺收益更新 → **生成报告：折线图显示播放上升、柱状图显示美食类收益最高 → 明确"你在赚钱，净收益+500，但纯风景类是雷区"** → 再生成脚本，选题偏美食探店。

## 1. 反馈闭环的输入

| 输入 | 来源 | 用途 |
|---|---|---|
| 产出记录 | output 表 | 反馈关联到哪条产出 |
| 真实指标 | 用户录入 | 播放/点赞/评论/收藏/转发 |
| 产出引用的资产 | output_asset 表 | 判断哪些资产被证明有效 |
| 产出涉及的店铺 | 产出内容中 place_ids | 回写店铺收益 |
| 博主画像 | blogger 表 | 写回 suit_type |
| 店铺库 | place 表 | 更新收益属性 |

## 2. 反馈闭环流程

```
  产出（脚本/视频/路线）
       │
       ▼
  录入真实指标（播放/点赞/评论/收藏/转发）
       │
       ▼
  ① Agent 分析：适合类型 / 踩雷点
       │  · 指标好坏
       │  · 内容特征（类型/风格/主题）
       │  · 该内容用了哪些资产（output_asset）
       │
       ├──────────────► ② 写回画像（blogger.suit_type）
       │
       ├──────────────► ③ 回写店铺收益（place.est_benefit 更新）
       │                   · 高数据产出 → 涉及店铺收益上调
       │                   · 低数据产出 → 涉及店铺收益下调
       │
       └──────────────► ④ 资产有效性标记（asset）
                           · 高数据产出引用的资产 → 标记"有效"
                           · 低数据产出引用的资产 → 标记"待审视"
       │
       ▼
  ⑤ 库进化（闭环核心 · 更新三库 + 算法 + 方向）
       │  · 知识库：金矿分类补强 / 雷区分类降权
       │  · 素材库：有效模板强化 / 无效模板降权
       │  · 算法库：验证的打法更新 / 证伪的打法修正
       │  · 方向：suit_type + knowledge_focus 更新
       │
       ▼
  闭环合上 ✓（再次建库/产出，结果已因反馈而变）
```

## 3. 核心：Agent 反馈分析决策（Agent 自主）

### 3.1 分析什么（Agent 读什么）

| 读什么 | 来源 | 为什么 |
|---|---|---|
| 指标数值 | 用户录入 | 判断表现好坏 |
| 产出类型/主题/风格 | output.content | 判断哪类内容表现好 |
| 产出用了哪些资产 | output_asset | 判断哪些资产有效 |
| 产出涉及哪些店铺 | output 中 place_ids | 判断哪些店赚钱 |
| 博主画像 | blogger | 判断与画像的关系 |

### 3.2 判断什么（Agent 输出）

**① 适合的视频类型 / 踩雷点**
```
基于：哪类内容数据好/差 → 判断博主适合什么、踩什么雷
示例：美食探店员数据好 → "适合：美食探店/沉浸体验"
      纯风景vlog数据差 → "踩雷：纯风景慢节奏"
```

**② 资产有效性**
```
产出引用哪些资产 + 数据好坏 → 判断哪些资产有效/待审视
示例：脚本A引用了"酸汤鱼做法"+"口播钩子模板"，数据好
     → 这两条资产标记"有效"
```

**③ 店铺收益回写**
```
该产出涉及的店铺 + 数据好坏 → 更新店铺收益属性
示例：凯里酸汤鱼店的探店视频 1万播放 800评论
     → est_benefit 上调（该店被证明能产生高数据内容）
```

**店铺关联路径（Agent 必须按此顺序找，找不到就诚实标注"未关联店铺"）**：

| 产出类型 | 路径（一步一步找） | 找什么 |
|---|---|---|
| route_rec | 产出 content 里已带 places[] | 直接用，最可靠 |
| script / storyboard | ① output.source_refs → 引用的 asset → asset 带 place_id 的取店 | 由资产反查店 |
| script / storyboard | ② （权威后补）产出 content 中标题/正文含店铺名 → 匹配 place 表 name 模糊命中 | 文本匹配兜底 |
| 任意 | 上面都没有 | 标记"未关联店铺"，不调收益 |

> **为什么用"反查/模糊匹配"而非输出直接带店**：脚本/分镜的产出提示词里没有强制输出店铺字段，但脚本常引用带 place_id 的知识/素材条目，所以**溯源链路是通的**。若 Agent 判断某条产出的主题明显是某店但找不到关联，反馈时应诚实标注"未关联店铺"，并提示补画像。

**④ 库进化（闭环核心 · 更新三库 + 算法 + 方向）**
```
数据证明哪类内容好/差 → 反哺更新库（不是只改一个画像字段）：
· 知识库：某主题数据好 → 该分类补强（追加可信条目/标重点）；数据差 → 该分类降权
· 素材库：某开头/钩子/模板被证明有效 → 强化标注+生成变体；被证明无效 → 降权/标待审视
· 算法库：某选题打法/平台机制被验证 → 更新条目（如"探店+非遗组合有流量"）；被证伪 → 修正
· 方向：suit_type 更新 → knowledge_focus/主攻方向同步更新 → 下次建库按新方向长满
```
> **这就是闭环的实质**：反馈反哺的是「库 + 算法 + 方向」整体，而不只是某个字段。下次建库/产出/推荐全部读更新后的库运行——"越用越懂"落地在库的进化上。

### 3.3 反馈分析提示词（可直接使用）

```
你是贵州文旅博主反馈分析 Agent。对以下产出 + 真实指标做反馈分析。

【博主画像】
{结构化画像}

【产出记录】
{output 内容：类型/主题/风格/引用资产/涉及店铺}

【真实指标】
{用户录入：views/likes/comments/collects}

【产出引用资产】
{output_asset：该产出用了哪些知识/素材/算法条目}

【产出涉及店铺】
{place：该产出涉及的店铺及当前收益属性}

【你的职责】
1. 分析博主适合的视频类型/踩雷点：
   基于哪类内容数据好/差，判断博主适合什么、踩什么雷
2. 判断资产有效性：
   产出引用哪些资产 + 数据好坏 → 标记"有效"/"待审视"
3. 更新店铺收益：
   按「店铺关联路径」确定产出涉及的店铺（§3.2）→ 建议收益上调/下调

【硬约束】
- 判断必须基于真实指标，不臆测
- 每个判断必须给出 reason
- 收益调整建议：高数据上调/低数据下调/持平，给出幅度理由
- 输出结构化 JSON

【输出格式】
{
  "decision": "反馈",
  "analysis": {
    "suit_type": "适合的美食探店/沉浸体验",
    "pitfalls": ["纯风景慢节奏是雷区"],
    "asset_effects": [
      {"asset_id":1, "title":"酸汤鱼做法", "effect":"有效", "reason":"产出数据好"}
    ],
    "place_effects": [
      {"place_id":1, "name":"凯里酸汤鱼店", "adjust":"up", "amount":200, "reason":"探店视频数据好"}
    ]
  },
  "summary": "一句话总结"
}
```

## 4. 表结构（反馈闭环的落点）

### 4.1 metric 反馈表（扩展）

```sql
CREATE TABLE metric (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  output_id    INTEGER NOT NULL REFERENCES output(id),
  views        INTEGER DEFAULT 0,
  likes        INTEGER DEFAULT 0,
  comments     INTEGER DEFAULT 0,
  collects     INTEGER DEFAULT 0,
  analysis     TEXT,              -- Agent分析结果(适合类型/踩雷点/资产有效性)
  decision_id  INTEGER,           -- 关联决策记录
  recorded_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.2 画像写回（blogger.suit_type 更新）

```sql
-- Agent 分析后更新博主画像适合类型
UPDATE blogger SET suit_type='美食探店/沉浸体验', updated_at=CURRENT_TIMESTAMP WHERE id=?
```

### 4.3 店铺收益回写（place 表更新）

```sql
-- 反馈后更新店铺收益属性
UPDATE place SET est_benefit=est_benefit+?, like_level=?, updated_at=CURRENT_TIMESTAMP WHERE id=?
```

### 4.4 资产有效性（asset 表扩展）

```sql
ALTER TABLE asset ADD COLUMN effect TEXT;  -- 有效|待审视|未评估
```

### 4.5 关系补充

```
output 1—n metric   （一条产出多条反馈）
metric n—1 decision_log （每次反馈关联一个决策记录）
```

## 5. 闭环生效（怎么证明"越用越懂"）

### 5.1 写回画像后，再次产出的变化

| 反馈前 | 反馈后（suit_type 更新） | 产出变化 |
|---|---|---|
| 画像无适合类型 | suit_type=美食探店 | 生成脚本 → 主题偏美食探店 |
| 画像 style=口播 | 反馈证明探店数据好 | 生成脚本 → 风格偏探店沉浸 |

### 5.2 回写店铺后，路线推荐的变化

| 反馈前 | 反馈后（est_benefit 更新） | 路线变化 |
|---|---|---|
| 凯里酸汤鱼店收益 800 | 探店数据好 → 收益上调至 1000 | 路线推荐 → 凯里店排更前 |
| 某店收益高但没人拍 | 低数据 → 收益下调 | 路线推荐 → 该店排后/移除 |

### 5.3 闭环证据（演示核心）

> 录真实指标"美食探店员 1万播放 800评论，纯风景 vlog 播放惨淡"→ 系统判"适合美食+探店，风景踩雷"→ 写回画像 → 相关店收益上调 → **再点生成脚本，选题/风格明显偏美食探店；再点推荐路线，凯里店排前**。

## 6. 报告生成（核心新增）

### 6.1 报告目标

**读指标表 → 详细数据分析 → 生成带图表的最终报告 → 告诉博主：赚没赚钱？亏没亏？流量怎么样？供应商怎么样？** 不只是一句分析，而是用图表呈现。

### 6.2 报告内容（四类指标 + 图表）

| 报告区块 | 数据来源 | 图表类型 | 回答的问题 |
|---|---|---|---|
| **钱 money** | indicator(money) + place 表 | 柱状图（收益/成本/净收益对比） | **赚钱还是亏钱？** |
| **流量 traffic** | indicator(traffic) + metric 表 | 折线图（播放趋势）+ 柱状图（互动率） | **流量涨了还是跌了？** |
| **产品 product** | indicator(product) + output 表 | 柱状图（内容类型分布） | **出了多少片？哪类内容多？** |
| **供应商 supplier** | indicator(supplier) + place 表 | 柱状图（店铺收益 Top） | **哪些店赚钱？合作得怎样？** |
| **建议** | Agent 综合分析 | 无图，文字 | 下一步做什么 |

### 6.3 图表数据来源（Agent 生成图表）

| 图表 | 数据来源 | 示例 |
|---|---|---|
| **折线图（流量趋势）** | metric 表按时间聚合 views/likes | 近 7 天播放量趋势 |
| **柱状图（收益对比）** | place.est_benefit - est_cost | 各店净收益对比 |
| **柱状图（内容分布）** | output 按 **category** 聚合 | 各内容分类出片数 |
| **柱状图（店铺收益 Top）** | place 按 est_benefit 排序 | 收益 Top 店 |

> **同一分类下**：脚本/分镜/路线均可共用一个 category（如"美食探店"），报告的内容分布柱状图按 category 聚合，较"按 type 聚合"更符合"博主在做什么内容"的业务语义。

### 6.4 报告 Agent 提示词（可直接使用）

```
你是贵州文旅博主经营报告 Agent。读取指标表 + 业务数据，生成带图表的最终经营报告。

【指标体系】
{indicator 表全部指标：类别/定义/公式/数据来源/目标/当前/趋势}

【业务数据（按指标数据来源取数）】
{place 表：店铺收益}
{metric 表：流量数据}
{output 表：内容产出}

【你的职责】
1. 读取指标表，按四类（钱/流量/产品/供应商）做详细数据分析
2. 对每个指标：当前值 vs 目标 vs 历史 → 判断达标/超标/亏损/趋势
3. 输出结论：
   - 赚钱没?亏钱没?（净收益/ROI）
   - 流量怎么样?（播放/互动趋势）
   - 内容产出如何?（各类数量/分布）
   - 供应商/店铺如何?（哪店赚钱/亏钱）
4. 生成图表数据：折线图（流量趋势）、柱状图（收益对比/内容分布/店铺Top）
5. 给出可执行建议

【硬约束】
- 图表数据必须来自真实业务表，不编造数字
- 每个结论必须给出 reason + 数据支撑
- 明确回答：赚钱/亏钱/盈亏平衡；流量健康/下滑
- 输出结构化 JSON

【输出格式】
{
  "decision": "报告",
  "conclusion": {
    "money": "赚钱中，净收益+500，ROI 1.8",
    "traffic": "播放量上升，近7天+30%",
    "product": "美食类10篇，景区2篇，美食为主",
    "supplier": "凯里酸汤鱼店收益最高(800)"
  },
  "charts": [
    {"type":"line", "title":"播放量趋势", "data":[[日期],[播放量]]},
    {"type":"bar", "title":"净收益对比", "data":["店名",[收益]]},
    {"type":"bar", "title":"内容类型分布", "data":["类型",[数量]]}
  ],
  "suggestions": [{"action":"多拍美食探店","priority":"高","reason":"播放量最高"}],
  "summary": "一句话总结：你在赚钱，美食类是你的金矿"
}
```

### 6.5 报告落库（report 表）

```sql
CREATE TABLE report (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id    INTEGER NOT NULL REFERENCES blogger(id),
  conclusion    TEXT,           -- 结论 JSON（money/traffic/product/supplier）
  charts        TEXT,           -- 图表数据 JSON
  suggestions   TEXT,           -- 建议 JSON
  decision_id   INTEGER,
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## 8. 落地执行步骤

```
Step 0 输入：用户对某条产出录入真实指标（views/likes/comments/collects）+ 定时自动回收平台数据
Step 1 Agent 反馈分析：按 §3.3 提示词分析（适合类型/踩雷点/资产有效性/店铺收益）
Step 2 落库：写 metric 表 + decision_log（decision_type=feedback）
Step 3 写回画像：更新 blogger.suit_type
Step 4 回写店铺：更新 place.est_benefit/like_level
Step 5 标记资产：更新 asset.effect（有效/待审视）
Step 6 更新指标：按 indicator.formula 从各表取数，更新 current/trend
Step 7 库进化：按 §3.2④ 更新三库（知识/素材/算法）+ 算法打法 + 创作方向（knowledge_focus）
Step 8 生成报告：读指标表 → Agent 按 §6.4 提示词生成图表报告 → 落 report 表
Step 9 展示：前端渲染经营报告（图表 + 赚钱/亏钱结论）+ 展示"你的库已更新"（三库/算法/方向的变化）
Step 10 闭环验证：再次建库/产出/推荐路线，结果已因反馈而变
```

## 10. 边界与约束

- **不臆测**：分析必须基于真实指标，不编造数据。
- **判断可解释**：每个判断附 reason。
- **收益调整留痕**：店铺收益调整记录在案，可追溯为什么变。
- **失败降级**：Agent 无法分析时返回明确错误，不写垃圾结果。
- **报告可对比**：多次报告对比，演示"数据变化 → 报告变化"。
