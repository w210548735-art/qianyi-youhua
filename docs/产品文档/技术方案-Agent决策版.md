# 贵客松 · 文旅博主 AI 赋能 Agent —— 技术方案（Agent 决策版）

| 项 | 内容 |
|---|---|
| 文档版本 | v0.2 |
| 撰写日期 | 2026-08-28 |
| 状态 | 待评审 |
| 定位 | 本文档是**提示词工程 + Agent 决策机制**的方案，不是写死的表结构。**一切结构由 Agent 依据博主信息实时决策** |

> **核心原则（用户 2026-08-28 强调）**：
> 表设计、存储、库间影响、有效性判断，**不是产品经理拍脑袋说了算**，而是「**提示词定规则框架 → Agent 根据博主信息实时决策 → 结果落库**」。
> 系统是"AI 说了算"。本方案只定义：给 Agent 什么样的提示词、Agent 有哪些决策权、决策结果如何落库可追溯。

---

## 0. 一句话架构

**Agent 是决策大脑，数据库是决策结果的落点，提示词是决策的规则宪法。**

```
博主信息（画像）
   │
   ▼
┌──────────────────────────────┐
│        Agent 决策层           │
│  · 建库决策：长什么、长多少、    │
│    怎么分类、可信度怎么标       │
│  · 体检决策：缺什么、哪不可信    │
│  · 产出决策：脚本结构、路线排序   │
│  · 反馈决策：适合类型、踩雷点    │
│  每个决策都产出「决策记录」      │
└──────────────┬───────────────┘
               │ 落库
               ▼
┌──────────────────────────────┐
│        数据层（落点）           │
│  画像 / 资产 / 产出 / 反馈 / 路线 │
│  加上「决策记录表」（可追溯）     │
└──────────────────────────────┘
```

**关键点**：Agent 不只是"生成内容"，Agent 是"做结构决策"——它决定这个博主的三库**长什么样**，而不是我们预设。

---

## 1. Agent 有哪些决策权（共 5 项）

| # | 决策权 | Agent 决定什么 | 依据输入 |
|---|---|---|---|
| D1 | **建库结构决策** | 三库各长多少条、分哪些分类、哪些分类优先长满、可信度怎么标 | 博主画像 + 种子数据 |
| D2 | **体检决策** | 知识库缺什么、哪些条目不可信、健康度打分 | 资产表现状 |
| D3 | **产出决策** | 脚本结构（时长/开头/分镜）、路线怎么排序、推荐哪个 | 画像 + 资产 |
| D4 | **反馈决策** | 博主适合类型、踩雷点 | 指标 + 产出内容 |
| D5 | **进化决策** | 画像哪些字段要更新、下次建库优先补什么 | 全部 |

**原则**：Agent 有**全部结构决策权**，产品只给**提示词框架**（规则、约束、优先级、示例），不给死答案。

---

## 2. 提示词设计（Agent 决策的"宪法"）

### 2.1 提示词分四层，层层约束但留决策空间

| 层 | 内容 | 目的 |
|---|---|---|
| **L1 角色与目标** | "你是贵州文旅内容 AI 架构师，为博主定制内容资产库" | 定义 Agent 身份 |
| **L2 输入** | 博主画像 + 种子数据 + 当前资产库现状 | 给它决策依据 |
| **L3 规则与约束** | 见下表（硬约束）+ 允许自由决策的范围 | 防止跑偏 |
| **L4 输出格式** | 结构化 JSON（分类/条目/可信度/决策理由） | 可落库、可追溯 |

### 2.2 硬约束（提示词里的规则，Agent 不能违反）

| 约束 | 内容 |
|---|---|
| 规则1 | **主领域长满，非主领域少量**：博主主领域优先长满（≥15条），非主领域少量（≤5条），不是平均生成 |
| 规则2 | **可信度必标**：每条必标来源档位（实锤/官方/推断/自编）+ 0-5 分，无来源的必须标低分 |
| 规则3 | **不编造**：知识库条目必须基于种子数据/可信来源，禁止凭空造景点/非遗 |
| 规则4 | **分类自定但可解释**：Agent 可自定义分类，但必须给出分类理由 |
| 规则5 | **可追溯**：每个决策输出 `reason`（决策理由），落库可查 |
| 规则6 | **失败降级**：Agent 无法决策时返回明确错误，不输出垃圾数据 |

### 2.3 提示词中允许 Agent 自由决策的范围（留给 Agent）

- 三库各长多少条（在硬约束内）
- 分类粒度（细到"酸汤鱼/长桌宴"还是粗到"非遗/美食"）
- 每条的可信度具体分值
- 体检的缺口清单与健康度评分标准
- 产出脚本的具体结构

## 3. 表设计（数据层 = Agent 决策的落点）

> **关键变化**：相比 v0.1，新增「决策记录表 decision_log」——因为 Agent 说了算，就必须**记录它说了什么、为什么**，否则无法追溯、无法复盘、无法演示"AI 说了算"。

### 3.1 表清单（6 张）

| 表 | 职责 | 谁写入 |
|---|---|---|
| **blogger** | 博主画像 | 用户填 + Agent 进化写回 |
| **asset** | 资产条目（三库统一，lib_type 区分） | **Agent 生成** + 人工增删改查 |
| **output** | 产出记录 | **Agent 生成** |
| **metric** | 反馈指标 | 用户录 + Agent 分析 |
| **route** | 路线商单 | 预置 + Agent 匹配 |
| **decision_log** | **决策记录**（Agent 每次决策 + 理由） | **Agent** |

### 3.2 blogger 画像表

| 字段 | 类型 | 谁写入 | 说明 |
|---|---|---|---|
| id | PK | 系统 | |
| name | text | 用户 | 博主名 |
| platform | text | 用户 | 平台 |
| content_type | text | 用户 | 内容类型（多选逗号分隔） |
| style | text | 用户 | 风格 |
| followers | int | 用户 | 粉丝量 |
| frequency | text | 用户 | 更新频率 |
| monetization | text | 用户 | 变现方式 |
| routes | text | 用户 | 常用路线 |
| viral_topic | text | 用户 | 最近爆款（Q7） |
| suit_type | text | **Agent 写回** | 适合的视频类型 |
| profile_state | text | **Agent 写回** | 画像完整度/待补字段 |
| created_at / updated_at | datetime | 系统 | |

> **Agent 决策点**：`suit_type`（适合类型）、`profile_state`（画像完整度）由 Agent 依据反馈/信息缺口写回——画像不是用户填死的，是 Agent 帮忙进化的。

### 3.3 asset 资产表（三库统一）

| 字段 | 类型 | 谁写入 | 说明 |
|---|---|---|---|
| id | PK | 系统 | |
| blogger_id | FK | 系统 | 属于哪个博主 |
| lib_type | enum | **Agent** | knowledge/material/algorithm（三库区分） |
| category | text | **Agent** | 分类（Agent 自定义，可解释） |
| title | text | **Agent** | 条目名 |
| content | text | **Agent** | 详细内容 |
| tags | text | **Agent** | 多标签逗号分隔 |
| source | text | **Agent** | 来源（实锤URL/官方/推断/自编） |
| credibility | int | **Agent** | 可信度 0-5 |
| decision_id | FK | 系统 | 关联到生成它的决策记录 |
| created_at / updated_at | datetime | 系统 | |

> **Agent 决策点**：`lib_type`、`category`、`source`、`credibility` 全部由 Agent 根据博主信息实时决定。

### 3.4 output 产出表

| 字段 | 类型 | 谁写入 | 说明 |
|---|---|---|---|
| id | PK | 系统 | |
| blogger_id | FK | 系统 | 属于哪个博主 |
| type | enum | **Agent** | script/storyboard/route |
| title | text | **Agent** | 产出标题 |
| content | text | **Agent** | 产出正文 |
| decision_id | FK | 系统 | 关联决策记录 |
| created_at | datetime | 系统 | |

### 3.5 metric 反馈表

| 字段 | 类型 | 谁写入 | 说明 |
|---|---|---|---|
| id | PK | 系统 | |

| analysis | text | **Agent** | 分析结果（适合类型/踩雷点） |
| recorded_at | datetime | 系统 | |

### 3.6 route 路线商单表

| 字段 | 类型 | 谁写入 | 说明 |
|---|---|---|---|
| id | PK | 系统 | |
| title | text | 预置 | 路线名 |
| locations | text | 预置 | 途经地点 |
| cost | int | 预置 | 预估成本 |
| benefit | int | 预置 | 预估收益 |
| fit_tags | text | 预置 | 契合标签 |
| suitable_type | text | 预置 | 适用博主类型 |

> route 是预置数据（种子），**Agent 负责匹配与排序**（不在表结构，在产出决策 D3）。

### 3.7 decision_log 决策记录表（Agent 说了算的可追溯性）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | PK | |
| blogger_id | FK | 哪个博主 |
| decision_type | enum | build/assess/generate/feedback/evolve |
| input_summary | text | 决策时看到了什么（画像/资产摘要） |
| decision | text | Agent 决定的内容（JSON） |
| reason | text | 决策理由 |
| created_at | datetime | |

> **为什么加这张表**：Agent 说了算 ≠ 黑盒。每次决策留痕，演示时可展示"Agent 为什么这么建库"，复盘时能看"决策是否合理"。这是产品"AI 说了算"的**可信度底座**。

## 4. 存储设计

| 项 | 方案 | 理由 |
|---|---|---|
| 数据库 | **SQLite** | 零部署、单文件、演示即插即用、事务/索引/FTS 够用 |
| 多选字段 | 逗号分隔存 text | MVP 简单，检索用 LIKE/FTS |
| 大文本 | text 直存 | 无压力 |
| 全文检索 | **先 LIKE 退路，FTS5 后做** | 够用优先 |
| 决策留痕 | decision_log 表 | Agent 说了算的可追溯 |

## 5. 库间影响（Agent 决策如何流动）

```
       ┌─────────────┐
       │  Agent 决策层 │  ← 一切影响的中枢
       └──────┬──────┘
              │ 读画像/资产 → 决策 → 写库
              ▼
  ┌─────────┐   ┌─────────┐   ┌─────────┐
  │ 知识库    │   │ 素材库   │   │ 算法库   │
  │(事实/可信)│   │(创作/风格)│   │(机制/规则)│
  └────┬────┘   └────┬────┘   └────┬────┘
       │     影响关系：知识→素材→产出，算法定结构
       ▼
  ┌─────────────────────────┐
  │      产出(脚本/路线)        │
  └───────────┬─────────────┘
              ▼
  ┌─────────────────────────┐
  │      反馈(指标→分析)        │
  └───────────┬─────────────┘
              ▼
  ┌─────────────────────────┐
  │      画像进化(suit_type)   │  ← 回到 Agent 决策，闭环
  └─────────────────────────┘
```

**影响规则（提示词硬约束）**：
1. **知识 → 产出**：产出脚本引用知识条目时必须带上该条目的可信度（可信度 <3 不得作为核心论据）。
2. **素材 → 产出**：脚本结构套用素材库对应风格模板。
3. **算法 → 产出**：算法库给产出"结构约束"（时长/钩子/标签）。
4. **反馈 → 画像**：反馈分析结果写回 suit_type。
5. **决策 → 全库**：每次决策落 decision_log，可追溯。

## 6. 有效性判断（Agent 决策，不是公式写死）

> **核心原则**：有效性判断 = 给 Agent 一套**判断规则提示词**，由 Agent 依据当前库现状实时评估。不预设固定公式。

### 6.1 Agent 评估提示词（判断规则的宪法）

```
你正在评估某位博主的资产库有效性。依据以下维度，结合当前库的实际内容给出判断：

【维度1 覆盖度】对比"该类博主应有的内容范畴"，判断当前库缺哪些类、覆盖了多少。
【维度2 可信度】检查每条资产的来源档位与 credibility，指出哪些不可信/来源不明。
【维度3 使用率】检查哪些资产从未被产出引用，指出冗余与缺口。
【维度4 匹配度】判断当前库与博主画像（内容类型/风格/变现）是否匹配，哪些方向过盛/过弱。

输出：缺口清单 + 可信风险 + 冗余清单 + 健康度评分(0-100) + 改进建议。
每个判断必须给出 reason（依据什么判断）。
```

### 6.2 有效性 = Agent 依据库现状的**实时判断**，而非固定公式

| 维度 | Agent 怎么判断 | 依据 |
|---|---|---|
| 覆盖度 | 对比博主该有的范畴，列出缺口 | 画像 + 库内容 |
| 可信度 | 检视每条 source/credibility，标风险 | 库内容 |
| 使用率 | 查哪些资产没被产出引用 | 产出引用关系 |
| 匹配度 | 判断库与画像是否对齐 | 画像 + 库 |

### 6.3 决策落库可追溯

每次体检 → Agent 产出评估 → 落 decision_log（decision_type=assess）+ 可回显给博主。

### 6.4 演示点（评委最认）

> 点【体检】→ Agent 输出"知识库覆盖度 60%，缺景区类；3 条无来源低可信；素材库 2 条未用建议清理；健康度 72 分"→ 每条判断附 reason → 录真实指标后再次体检，**Agent 判断真的变了**（因为库变了）。
