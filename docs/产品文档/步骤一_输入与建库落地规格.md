# 步骤一 · 输入层 → 建库落地规格

> 版本 v0.1 · 2026-08-28
> 定位：**可执行规格**。任何 Agent / 开发者读了本文档，必须能实现"输入博主信息 → 建立完整知识库表 + 表间关系 → 可落地可检索可增删改查"。
> 本文档 = 采集设计 + 画像→建库翻译规则 + Agent 决策提示词 + 精确表结构 + 表间关系 + 落地步骤 + 验收标准。

---

## 0. 本步骤的目标（可验收）

输入一个博主的**基础信息**，系统能自动完成：
1. 建立该博主的**知识库**（含三库：知识/素材/算法）与**画像表**
2. 建出**表结构**（DDL）与**表间关系**
3. 生成**初始条目**（20-30 条，主领域长满）
4. 条目**可检索、可增删改查**
5. 所有决策**可追溯**（decision_log）

**验收线**：一份"非遗美食博主"画像 → 系统产出完整三库 → 关系清晰 → 检索"酸汤鱼"能命中。

---

## 1. 输入采集设计（多轮对话）

> **核心原则**：博主信息不是一次性填表单，而是通过 **Agent 多轮对话**逐步采集。Agent 像一位懂行的编辑/策划，顺着博主的语境一问问下去，30 秒完成基础画像，过程中根据回答动态调整下一问。

### 1.0 对话整体流程

```
Agent 开场白（价值钩子，30 字）
       │
       ▼
┌─────────────────────────────────┐
│ 第一轮 · 必填（5 问，链式推进）      │
│  Q1 平台 → Q2 内容 → Q3 风格    │
│  → Q4 粉丝 → Q5 变现            │
│  每问根据上一回答动态调整措辞        │
└──────────────┬──────────────────┘
               ▼
┌─────────────────────────────────┐
│ 第二轮 · 可选（2-3 问，价值驱动）    │
│  Q6 路线 → Q7 爆款 → Q8 频率     │
│  "你常跑哪些地方？"                │
│  "最近有没有一条爆款？"            │
│  博主不答也不强求，直接跳过          │
└──────────────┬──────────────────┘
               ▼
┌─────────────────────────────────┐
│ 第三轮 · 确认与价值兑现             │
│  Agent 复述："好的，我记住了"      │
│  + 当场给一个价值钩子               │
│  "根据你的画像，建议你先做          │
│   非遗美食探店方向"                │
└──────────────┬──────────────────┘
               ▼
          采集完成 → 进入建库
```

### 1.1 对话设计细节

#### 1.1.1 Agent 开场白（价值钩子）

> "你好！我是你的贵州内容 AI 助手。我想先了解你，这样我帮你建的库、写的脚本、推的商单路线才会对。回答几个简单问题，30 秒搞定。"

**设计要点**：不说"填表"、"问卷"、"注册"，说"了解你"、"帮你建库"。博主不是在被调查，是在被"懂行的人"请教。

#### 1.1.2 第一轮 · 必填 5 问（链式推进，逐问调整）

**Q1 · 平台**
> "你主要在哪个平台做？抖音、小红书、B站，还是多平台都发？"

| 博主回答 | Agent 行为 |
|---|---|
| 抖音 | 记录 platform=抖音，后续算法库侧重抖音机制 |
| 小红书 | 记录 platform=小红书，后续算法库侧重图文+笔记 |
| 多平台 | 记录 platform=多平台，后续算法库侧重跨平台策略 |

**Q2 · 内容类型**（根据 Q1 调整措辞）
> "你主要拍贵州的什么？是跑景区景点，还是挖巷子里的美食，或者做非遗手艺、民俗节庆？"

**追问策略**：博主说"美食" → 追问"偏探店还是偏做法教学？"；博主说"都做" → "你粉丝最认你哪个方向？"

**Q3 · 风格**（根据 Q2 调整措辞）
> "你用哪种方式拍？是比较像朋友聊天那样口播，还是沉浸式 vlog，或者剧情演绎？"

**追问策略**：博主犹豫 → 给例子："比如有些博主是边走边说的探店 vlog，有些是直接对着镜头测评口播。"

**Q4 · 粉丝量级**（不问精确数，给档位）
> "你现在大概多少粉丝？1k 以下、1万、10万，还是更大？不问精确数字，就一个范围，方便我帮你判断接什么量级的商单。"

**Q5 · 变现方式**（根据 Q4 调整措辞）
> "你现在靠什么变现？接商单、带货、还是探店置换？或者刚开始做，暂时不接？"

> **第一轮结束后，Agent 应已有完整的基础画像（5 字段全）。**

#### 1.1.3 第二轮 · 可选 2-3 问（价值驱动，不答不强求）

**Q6 · 常用路线**（用建议替代提问）
> "你平时有固定跑的路线吗？比如常跑黔东南、或者常蹲某个菜市场？有的话告诉我，没有的话我后面根据你的类型帮你推荐。"

**设计要点**：用"建议替代提问"——"没有的话我帮你推荐"降低了博主的回答压力。

**Q7 · 最近爆款**（**最值钱的一问**）
> "最近有没有一条数据特别好的内容？比如哪条突然爆了？你告诉我，我记下来，建库的时候重点帮你收这个方向。"

**设计要点**：给"爆款"一个具体定义（"数据特别好"），降低歧义。同时给出利益（"建库重点收"）。

**Q8 · 更新频率**
> "你更新频率怎么样？日更、周更，还是随缘？"

**设计要点**：用"随缘"替代"不定期"，更口语化，博主更有共鸣。

> **第二轮后，Agent 可跳过不答的字段，用默认值/系统推断填补。**

#### 1.1.4 第三轮 · 确认与价值兑现

> "好的，我记住了。你是在 **{平台}** 做 **{内容类型}** 的博主，风格偏 **{风格}**，粉丝在 **{量级}**，靠 **{变现}** 变现。"
>
> "根据你的画像，我建议你先从 **{主方向}** 切入，你的内容库我会重点建这个方向。"

**设计要点**：复述让博主感到被记住。价值钩子（"建议你先做 X"）让博主觉得"30 秒填值了"。

#### 1.1.5 对话中 Agent 的动态行为规则

| 场景 | Agent 行为 |
|---|---|
| 博主回答模糊（"就随便拍拍"） | 追问："你粉丝最认你哪类内容？" |
| 博主跳过问题 | 不追问，记录空值，用系统推断填补 |
| 博主回答与之前矛盾 | 追问确认："你刚刚说偏美食，现在说偏景区，哪个更多一些？" |
| 博主不耐烦 | 收尾："好的，这些就够了，后面我帮你建库再细聊。" |
| 博主说"我不懂这些" | 解释："没事，举个例子：你平时拍的是景点打卡，还是做菜吃饭？" |

### 1.2 必填字段（5 个，多轮对话必须采集到）

| # | 字段 | 类型 | 选项 | 用途 |
|---|---|---|---|---|
| Q1 | 平台 platform | 单选 | 抖音/小红书/B站/视频号/多平台 | 算法库侧重 |
| Q2 | 内容类型 content_type | 多选 | 非遗文化/美食探店/景区打卡/民俗节庆/山地户外/少数民族风情/方言趣事/旅行攻略 | 知识库主攻方向 |
| Q3 | 风格 style | 单选 | 口播解说/vlog纪实/沉浸体验/剧情演绎/测评干货/图文分享 | 素材库主攻方向 |
| Q4 | 粉丝量级 followers | 单选档位 | 1k以下/1k-1万/1万-10万/10万+ | 算法库成长打法 |
| Q5 | 变现方式 monetization | 多选 | 平台流量/商单植入/带货/探店置换/知识付费/暂不接 | 路线推荐倾斜 |

### 1.3 可选字段（2-3 个，多轮对话价值驱动）

| # | 字段 | 类型 | 示例 | 价值 |
|---|---|---|---|---|
| Q6 | 常用路线 routes | 开放 | "常跑黔东南" | 路线推荐精准 |
| Q7 | 最近爆款 viral_topic | 开放一句话 | "酸汤鱼探店那期爆了" | **最值钱**，反哺素材+知识库 |
| Q8 | 更新频率 frequency | 单选 | 日更/周更/不定期 | 算法库发布节奏 |

### 1.4 对话 → 结构化数据转换规则

多轮对话自由文本 → 落库字段，Agent 需遵循：

| 博主回答（自然语言） | Agent 转换规则 | 落库结果 |
|---|---|---|
| "我主要在抖音做" | 映射到平台枚举 | platform="抖音" |
| "主要拍美食，偶尔探店" | 识别主次，主领域在前 | content_type="美食,探店" |
| "就是那种边走边说的" | 匹配到风格枚举 | style="vlog纪实" |
| "粉丝不到一万" | 映射到档位 | followers=1000 |
| "接商单、也接探店" | 识别多种变现 | monetization="商单,探店" |
| "我常跑黔东南那条线" | 直接保留原文（开放字段） | routes="黔东南线" |
| "酸汤鱼探店那条爆了" | 保留原文+抽关键词 | viral_topic="酸汤鱼探店" |
| "一周更新两条" | 映射到频率档位 | frequency="周更" |

**转换约束**：
1. **枚举字段必须映射到预定义档位**（平台/风格/频率），映射不了 → 归入"其他"并记录。
2. **开放字段保留原文**，不强行结构化。
3. **主次识别**：多选字段博主说"主要 X，偶尔 Y" → 主领域在前，Agent 建库时按顺序分配权重。
4. **对话记录保留**：原始对话写入 decision_log 的 input_summary，可回溯"博主原话是什么"。

### 1.5 多轮对话提示词（Agent 可直接使用）

```
你是贵州文旅博主画像采集 Agent。用多轮对话采集博主信息，30 秒完成基础画像。

【采集目标】5 个必填 + 2-3 个可选字段：
  必填: platform, content_type, style, followers, monetization
  可选: routes, viral_topic, frequency

【对话规则】
1. 用自然、懂行的口吻提问，不说"填表/问卷/注册"，说"了解你/帮你建库"
2. 逐问推进，根据上一回答动态调整下一问措辞
3. 博主答得模糊→追问一次；跳过→不强求，记空值
4. 博主不耐烦→收尾："这些就够了，后面建库再细聊"
5. 每问不要超过一句，不要一次抛多个问题

【开场白】
"你好！我是你的贵州内容 AI 助手。先想了解你一下，这样我帮你建的库、写的脚本、推的商单路线才会对。回答几个简单问题，30 秒搞定。"

【转换规则】
- 枚举字段映射到预定义档位，映射不了→"其他"并记录
- 开放字段保留原文
- 多选字段识别主次，主领域在前
- 原始对话写入 decision_log 的 input_summary

【输出】结构化画像 JSON：
{
  "platform": "...",
  "content_type": "主,次",
  "style": "...",
  "followers": 整数档位,
  "monetization": "主,次",
  "routes": "原文或空",
  "viral_topic": "原文或空",
  "frequency": "..."
}
```

## 2. 画像 → 建库指令翻译（规则表）

**Agent 依据画像字段，生成一份「建库指令」**。每个字段翻译成建库信号：

| 画像字段 | 翻译成建库信号 | 长进哪个库 |
|---|---|---|
| content_type=非遗+美食 | 知识库主攻非遗美食，**长满**，其它分类降权 | 知识库 |
| style=口播 | 素材库主攻口播模板/爆款开头/钩子 | 素材库 |
| platform=抖音 | 算法库主攻抖音机制/时长/标签 | 算法库 |
| followers=1万-10万 | 素材补"此量级打法"；算法补"此量级流量逻辑" | 素材+算法 |
| monetization=商单+探店 | 知识补商单/探店内容；路线向可接商单地域倾斜 | 知识+路线 |
| viral_topic=酸汤鱼探店 | 素材库收录该选题/开头手法；知识库补强该品类 | 素材+知识 |

**建库指令示例**（Agent 输出的结构化 JSON）：
```json
{
  "knowledge_focus": ["非遗美食"],
  "material_focus": ["口播模板", "爆款开头"],
  "algorithm_focus": ["抖音机制"],
  "priority_category": ["非遗", "美食"],
  "growth_stage": "1万-10万",
  "commercial_slant": ["探店", "商单"],
  "seed_viral": "酸汤鱼探店"
}
```

## 3. Agent 建库决策提示词（可直接使用）

### 3.1 建库主提示词

```
你是贵州文旅内容 AI 架构师。为以下博主定制内容资产库。

【博主画像】
{结构化画像}

【种子数据】
{贵州文旅可信种子条目：非遗/美食/景区/方言等，来自调研实锤}

【你的职责】
根据博主画像 + 种子数据 + 店铺信息，为博主建立三库（知识/素材/算法）+ 店铺库 + **指标体系**：
1. 决定三库各长多少条、分哪些分类、哪些分类优先长满
2. 为每条资产标注：所属库、分类、标题、内容、标签、来源档位、可信度(0-5)
3. **建立店铺库**：把种子/对话中提到的店与地点建为 place 实体（名称/类别/位置/招牌/喜爱度/预估收益/是否适合KOC与拍摄）
4. **店贯穿三库**：与店相关的知识/素材/算法条目，用 place_id 关联到对应店铺
5. **建立指标体系**（规范化，四类齐全）：
   - 钱 money：总收益/总成本/净收益/ROI/商单收入
   - 流量 traffic：总播放/平均播放/互动率/涨粉
   - 产品 product：出片数/更新频率/内容类型分布
   - 供应商 supplier：合作店铺数/单店平均收益/店铺收益分布
   每个指标含：名称/类别/定义/计算公式/数据来源/目标值/当前值/趋势
6. 决策必须可解释（每条/每类给出 reason）

【硬约束】
- 主领域长满(≥15条)，非主领域少量(≤5条)
- 可信度必标：实锤=5,官方=4,推断=3,自编=1
- 不编造：知识库条目必须基于种子数据/可信来源
- 店铺收益属性必标：est_cost/est_benefit/fits_koc/fits_shoot
- 指标体系四类必建（money/traffic/product/supplier），每个指标有计算公式与数据来源
- 分类可自定义但必须给理由
- 输出结构化 JSON

【输出格式】
{
  "decision": "建库",
  "structure": { "knowledge": [...分类...], "material": [...], "algorithm": [...] },
  "places": [
    { "name":"凯里酸汤鱼店", "category":"美食店", "location":"凯里", "specialty":"酸汤鱼",
      "like_level":5, "est_cost":200, "est_benefit":800, "fits_koc":1, "fits_shoot":1,
      "tags":["酸汤鱼","凯里"], "source":"实锤", "reason":"博主常去+商单价值高" }
  ],
  "assets": [
    { "lib_type":"knowledge|material|algorithm", "category":"...", "title":"...",
      "content":"...", "tags":["..."], "source":"实锤|官方|推断|自编", "credibility":4,
      "place_id":1, "reason":"..." }
  ],
  "indicators": [
    { "name":"净收益", "category":"money", "definition":"总收益-总成本",
      "formula":"SUM(est_benefit)-SUM(est_cost)", "data_source":"place表",
      "target":5000, "current":1200, "trend":"上升" }
  ],
  "summary": "本库覆盖：...；主攻：...；店铺库：...；指标：...；说明：..."
}
```

### 3.2 生成数量与倾斜规则（提示词内）

| 条件 | 规则 |
|---|---|
| 主领域（内容类型） | 知识库 ≥15 条 |
| 非主领域 | ≤5 条 |
| 风格（素材库） | 主风格模板 ≥5 条 |
| 平台（算法库） | 主平台机制 ≥3 条 |
| 总量 | 20-30 条 |

## 4. 精确表结构（DDL，Agent 直接落地）

### 4.1 blogger 画像表

```sql
CREATE TABLE blogger (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  name         TEXT NOT NULL,
  platform     TEXT,               -- 平台
  content_type TEXT,               -- 内容类型(逗号分隔)
  style        TEXT,               -- 风格
  followers    INTEGER,            -- 粉丝量(档位数字)
  frequency    TEXT,               -- 更新频率
  monetization TEXT,               -- 变现方式(逗号分隔)
  routes       TEXT,               -- 常用路线
  viral_topic  TEXT,               -- 最近爆款主题
  suit_type    TEXT,               -- 适合的视频类型(Agent写回)
  profile_state TEXT,              -- 画像完整度(Agent写回)
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.2 asset 资产表（三库统一，核心）

```sql
CREATE TABLE asset (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id   INTEGER NOT NULL REFERENCES blogger(id),  -- 属于哪个博主
  lib_type     TEXT NOT NULL,     -- knowledge|material|algorithm(三库区分)
  category     TEXT NOT NULL,     -- 分类(Agent自定义)
  title        TEXT NOT NULL,     -- 条目名
  content      TEXT NOT NULL,     -- 详细内容
  tags         TEXT,              -- 多标签(逗号分隔)
  source       TEXT,              -- 来源档位: 实锤|官方|推断|自编
  credibility  INTEGER DEFAULT 3, -- 可信度 0-5
  place_id     INTEGER,           -- 关联店铺实体(可空:该资产属于哪个店)
  decision_id  INTEGER,           -- 关联决策记录(可追溯)
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

> **place_id**：知识/素材/算法条目可关联到具体店铺。如"知识库—凯里酸汤鱼店的文化"→place_id=1，"素材库—凯里酸汤鱼店拍摄模板"→place_id=1，"算法库—探店类爆款规律"→place_id 可空（平台通用）。这样"店"贯穿三库，检索一家店能拿到它的知识+素材+算法三条线。

### 4.3 output 产出表

```sql
CREATE TABLE output (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id   INTEGER NOT NULL REFERENCES blogger(id),
  type         TEXT NOT NULL,     -- script|storyboard|route
  title        TEXT NOT NULL,
  content      TEXT NOT NULL,
  decision_id  INTEGER,           -- 关联决策记录
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

CREATE TABLE metric (

### 4.5 place 店铺实体表（贯穿三库，带收益属性）

> **核心新增**：店铺是博主接商单/拍内容的实体对象。博主的"喜欢的店、收益高的店"都记录在这里。知识/素材/算法条目都可通过 place_id 关联到具体店。店铺带**收益属性**，用于路线推荐时做**收益最大化**排序。

```sql
CREATE TABLE place (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id  INTEGER NOT NULL REFERENCES blogger(id),  -- 属于哪个博主的店铺库
  name        TEXT NOT NULL,        -- 店名/地点名
  category    TEXT,                 -- 类别: 美食店/非遗工坊/景区/民宿/民俗体验
  location    TEXT,                 -- 位置/地址
  specialty   TEXT,                 -- 招牌/特色
  like_level  INTEGER DEFAULT 3,    -- 博主喜爱度 1-5(博主主观)
  est_cost    INTEGER DEFAULT 0,    -- 预估成本(路费/餐费/拍摄成本)
  est_benefit INTEGER DEFAULT 0,    -- 预估收益/商单价值
  fits_koc    INTEGER DEFAULT 0,    -- 是否适合KOC商单 (0/1)
  fits_shoot  INTEGER DEFAULT 0,    -- 是否适合拍摄 (0/1)
  tags        TEXT,                 -- 标签(逗号分隔)
  source      TEXT,                 -- 来源: 博主提供/Agent推荐/实锤
  credibility INTEGER DEFAULT 3,    -- 可信度 0-5
  decision_id INTEGER,              -- 关联决策记录
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

> **收益属性（核心）**：`est_cost`（成本）、`est_benefit`（预估收益）、`fits_koc`（适合KOC商单）、`fits_shoot`（适合拍摄）。路线推荐 = 在这些店的收益属性上做**收益最大化**排序（见步骤三）。

  locations     TEXT,

);

### 4.7 indicator 指标体系表（步骤一建库时建立，规范化四类）

> **核心新增**：指标在步骤一建库时由 Agent 建立（根据博主画像+商业目标决定监控哪些指标），分四类：**钱 money / 流量 traffic / 产品 product / 供应商 supplier**。后续报告（步骤四）读取此表做数据分析并生成图表报告。

```sql
CREATE TABLE indicator (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  blogger_id  INTEGER NOT NULL REFERENCES blogger(id),
  name        TEXT NOT NULL,         -- 指标名，如"净收益"
  category    TEXT NOT NULL,         -- 类别: money|traffic|product|supplier
  definition  TEXT,                  -- 定义: 一句话
  formula     TEXT,                  -- 计算公式,如 SUM(est_benefit)-SUM(est_cost)
  data_source TEXT,                  -- 数据来源: place表|metric表|output表
  target      REAL,                  -- 目标值
  current     REAL,                  -- 当前值(报告时更新)
  trend       TEXT,                  -- 趋势: 上升|下降|持平
  decision_id INTEGER,               -- 关联决策记录
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

> **四类指标规范**：
> - **money 钱**：总收益 / 总成本 / 净收益 / ROI / 商单收入（来源 place 表）
> - **traffic 流量**：总播放 / 平均播放 / 互动率 / 涨粉（来源 metric 表）
> - **product 产品**：出片数 / 更新频率 / 内容类型分布（来源 output 表）
> - **supplier 供应商**：合作店铺数 / 单店平均收益 / 店铺收益分布（来源 place 表）

### 4.8 decision_log 决策记录表（可追溯底座）

```sql

  decision_type TEXT NOT NULL,    -- build|assess|generate|feedback|evolve|report
  input_summary TEXT,             -- 决策时看到的输入摘要
  decision      TEXT,             -- Agent决定的内容(JSON)
  reason        TEXT,             -- 决策理由
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 6.1 检索（先 LIKE，后 FTS5）
```sql
-- 按博主+三库检索
SELECT * FROM asset WHERE blogger_id=? AND lib_type=?
-- 关键词检索
SELECT * FROM asset WHERE title LIKE '%酸汤鱼%' OR content LIKE '%酸汤鱼%' OR tags LIKE '%酸汤鱼%'
-- 按分类过滤
SELECT * FROM asset WHERE blogger_id=? AND category=?
-- 按可信度过滤
SELECT * FROM asset WHERE blogger_id=? AND credibility<3
-- 按店铺检索(贯穿三库: 该店的知识+素材+算法条目)
SELECT * FROM asset WHERE blogger_id=? AND place_id=?

SELECT * FROM place WHERE blogger_id=? ORDER BY est_benefit DESC  -- 按收益排序
SELECT * FROM place WHERE blogger_id=? AND fits_koc=1           -- 适合KOC的店
SELECT * FROM place WHERE blogger_id=? AND like_level>=4        -- 博主喜欢的店

## 7. 落地执行步骤（Agent 照做）

```

   1b 对话自然语言经 §1.4 转换规则映射为可落库的结构化画像

Step 3 Agent 建库：读「指令 + 种子数据」→ 按 §3 提示词生成三库资产 + 店铺库 + **指标体系**

## 9. 边界与约束

- **MVP 单博主**：不建用户/账号体系。
- **种子数据**：来自调研总档的贵州文旅实锤（非遗/美食/景区/方言），来源标注真实。
- **失败降级**：Agent 无法建库时返回明确错误，不写垃圾数据。
- **决策留痕**：所有 Agent 决策写 decision_log，可追溯可演示。
